# Architecture

The installed Electron desktop window starts the bundled Python backend on an ephemeral loopback port and stops it on exit. The backend remains the SQLite state owner. Desktop data lives under `$XDG_DATA_HOME/clan-hub-crea-manager`; first launch copies legacy `data/` without deleting it. The source collection stays read only and is configured separately. The web build remains for future mobile synchronization.

The Linux desktop launcher passes `--ozone-platform=x11` so Electron uses XWayland. A minimal external-drag experiment showed that native Wayland yielded an empty receiver payload for both `file` and `files: [file]`, while XWayland delivered readable formatted JPEGs from both host and Flatpak portal paths. The backend, source library, and database remain unchanged by this display choice.

The Python standard-library HTTP server owns application state in SQLite. Pillow decodes and formats images. React and Vite provide the local gallery UI. The server binds to `127.0.0.1` and does not publish source files through an endpoint.

`Crea/` contains immutable originals. `data/app.sqlite`, `data/formatted/`, `data/thumbnails/`, and `data/tmp/` are separate ignored outputs. Import records use stable UUIDs derived from source-relative paths and SHA-256 content hashes. Image outputs are written to temporary files and atomically replaced. Formatting settings and creator colors are database state; render keys avoid reprocessing unchanged assets. Future staging and synchronization must use this backend as their authoritative state.

API: `POST /api/import` scans the collection; `GET /api/state` reports counts and creators; `GET /api/assets?status=ready|review` lists assets and render keys; `GET /api/image/:id/thumb|formatted` serves derived files; `POST /api/creators/:name/color` saves a color; `POST /api/assets/:id/format` saves fit/crop settings. The app is local-only; remote access requires a later authenticated transport. The frontend serves the gallery at `/` and creator color settings at `/settings`.

Staging adds durable `packages` and `package_items` tables and an `assets.used` flag. `GET /api/staging` returns Hot, Reserve, and Used counts. Package actions under `/api/staging` add or remove Hot items, move Hot to Reserve, activate Reserve with an atomic swap, save submission text, acknowledge review, and confirm Hot. `GET /api/assets?status=used` and `POST /api/used/restore` manage Used Crea. The backend performs confirmation and replenishment in one SQLite transaction. Clipboard copying is a client action; it never changes asset availability.

Creator visibility is stored in `creators.enabled`, defaulting to on for existing rows. `POST /api/creators/:name/enabled` changes it. Gallery and Used Crea asset queries, visible counts, and new staging selections respect it; existing packages and asset usage remain unchanged.

Electron's sandboxed renderer uses a narrow preload bridge to request a native package drag by package ID. The main process verifies the current Hot package through the loopback backend and resolves only formatted XDG files. If Discord is installed as a Flatpak, the main process exports each derived file read-only to `com.discordapp.Discord` through the Flatpak document portal and passes the resulting portal paths to `webContents.startDrag`; otherwise it passes host paths. A failed portal export prevents the drag. Deployment confirmation persists before and after snapshots of package membership and used IDs in `deployments` within the same SQLite transaction. `POST /api/staging/deployments/undo` restores the prior state only when it matches the saved post-deployment snapshot.

The desktop process mirrors authoritative Hot package membership into the fixed `$XDG_DATA_HOME/clan-hub-crea-manager/hot-staging/` directory. It polls the backend after startup and every second, copying formatted JPEGs to numbered filenames with atomic replacement and removing only obsolete managed copies. Missing images are omitted and reported. Dolphin opens this ordinary host folder and handles the drag into Flatpak Discord through its FileTransfer integration. The folder persists when Hot is empty; no staging or usage state changes until manual confirmation.

Hot Staging has a ten-item cap enforced inside the add transaction. Existing package membership and submission state are unchanged by the current UI layout.

Mobile uses the same React build at `/mobile` and the same authoritative staging API. The Electron backend binds fixed loopback port 8765 while the desktop window runs; private Tailscale Serve terminates HTTPS at the Framework's MagicDNS hostname and proxies to that port. The backend discovers the hostname from local Tailscale status. Remote requests require a one-time desktop-generated pairing code, then an HTTP-only secure cookie backed by a revocable SQLite session. The remote API allowlist covers visible assets, thumbnails, state, Hot/Reserve operations, and Hot confirmation; administrative actions remain excluded. Mobile confirmation requires the observed package ID and asset IDs, checked inside the existing deployment transaction. The mobile layout has only gallery, Hot, Reserve, and bottom search/filter controls. Both clients poll staging; the desktop mirrors Hot to Dolphin. No mobile mutations are queued while disconnected.

The mobile branch gallery uses Embla v8 with seven persistent slides. Each slide owns its vertical scroll and collapsible type state. Package touch drags use dnd-kit sensors; they submit the existing staging actions only on a valid drop. A Hot-to-Reserve request carries the observed package ID, which the backend checks within the move transaction. Reserve activation already checks the target Reserve package ID and swaps Hot atomically. The phone discards canceled or disconnected drags without a mutation.

The desktop package clipboard uses a small host Python/Qt helper running with XWayland. It validates the current Hot package, opens its formatted JPEGs through the FileTransfer portal, and advertises both `text/uri-list` and `application/vnd.portal.filetransfer` on the Framework clipboard. The helper remains alive to own the clipboard and transfer session. The mobile client submits a package-ID clipboard request to the backend; Electron polls and executes it, then reports status. The phone never receives full images or file paths for this operation. Clipboard success arms the phone's confirmation button but does not change usage state; a second tap submits the checked Hot confirmation.
